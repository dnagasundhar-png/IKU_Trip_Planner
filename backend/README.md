# Back end

FastAPI service that stores trips and places, generates a day-by-day itinerary with Gemini,
flags public holiday closures, and costs every item in local and home currency.

> Trips, places and itineraries are stored in Tiger Data (Postgres + TimescaleDB).
> Itineraries are generated by Gemini, checked against public holidays and real opening hours, and timed so there's room to travel between stops, around the traveller's own flights/trains and from where they're staying. Every item is costed per person in local currency and converted to the home currency. Changes made on the itinerary page get the same checks and are saved.

**Live API:** https://api.tripezium.club (interactive docs at https://api.tripezium.club/docs). Allowed browser origins: `https://tripezium.club`, `https://www.tripezium.club`, `https://tripezium.vercel.app`, 

## How imported places are used

- Places the user confirmed (`POST /trips/{id}/places`, `origin='import'`) go into the prompt as a JSON
  **data block**, with an instruction to treat it strictly as data. Delimiter text is stripped from imported
  names and tips first, so a caption can't break out of the block (prompt-injection guard).
- Gemini must reference them by their own `placeId`. If any are left out (and they could plausibly fit,
  about 3 a day), the same single fix pass asks Gemini to add them.
- Imported places with no coordinates get Gemini's approximate ones, so they can go on the map.
- Stops Gemini adds itself are saved as places with `origin='ai'` and replaced on each regeneration.

## Only real cities

Route cities are checked against the same per-country lists the front end's dropdown uses
(`frontend/public/cities/<CC>.json`: [GeoNames](https://www.geonames.org/) places with 1,000+ people, plus popular
spots). Accents and case are ignored and the list's spelling is saved ("kyoto" -> "Kyoto"). Anything else is
rejected with 422 `unknown_city`, so a stale draft or a direct API call can't create a trip to "Atlantis".
Countries without a list aren't blocked.

## How money is handled

- **Gemini estimates local costs per person. Code does all conversion and totals** (`services/budget.py`,
  `Decimal` throughout, rounded half-up to the penny). Day and trip totals are sums of the rounded item
  values, so the numbers the user sees always add up.
- **Rates** (`services/fx.py`): cache (last 6h in the `fx_rates` hypertable) -> Frankfurter (ECB reference
  rates, no key, fetched against EUR for full precision) -> hardcoded fallback (ECB snapshot from
  2026-10-16 for 29 currencies), so the demo never breaks if the API is down.
- Every live rate is stored in `fx_rates`, which gives us FX history (e.g. for a rate chart).

## How opening hours are handled

1. **Holidays:** Nager.Date public holidays for every year the trip touches (cached in the `holidays` table)
   go into the prompt, along with each date's weekday and guidance on weekly and seasonal closures.
2. **Opening hours (optional, `GOOGLE_MAPS_API_KEY`):** each stop's weekly hours are looked up with the
   Google Places API (New). **Google is used only for opening hours**: the field mask is
   `places.regularOpeningHours`, we never use Google names or coordinates, and nothing from Google is stored.
   Plain code checks the whole visit (start + duration) fits inside the hours on that weekday.
3. **One fix pass:** any stop that is closed (per the hours, or marked closed by Gemini) is sent back to
   Gemini once to be moved or replaced. If it's still closed afterwards it's shown as `closed`.
4. **Closure check (deterministic):** on a public holiday, closure-prone stops (museum, shop, market,
   restaurant, cafe, bank, office, gallery) that are `ok` become `check_hours`. `closed` is never changed.

Final status: opening hours can only make a status more cautious, never less (weekly hours can't see seasonal
closures). Hours say closed -> `closed`; key set but no hours found -> `check_hours` (except open-air
`landmark`/`park` stops like streets and crossings); otherwise Gemini's status.
Google can't tell us holiday hours months ahead, hence step 4.

## Travel time between stops

Estimated in code from coordinates (`services/travel.py`, mirrored in `frontend/lib/travel.ts`), no routing API:
straight-line distance x 1.3 for streets, then walking (4.5 km/h, for short hops), public transport
(+10 min to reach the station and wait, 25 km/h) or, beyond 40 km, train (+20 min, 80 km/h), rounded up to
5 minutes. We compared it with Google's public transport times for 21 trips in London, Paris and Seoul: 12 were
within 5 minutes, and most of the rest we underestimated, by up to 19 minutes, on hilly or awkward cross-town
trips. (Google gives no public transport routes in Japan at all.)

After Gemini plans, stops that don't leave enough time are **pushed later, never earlier**. A day that then runs
past the traveller's day end goes to the same single fix pass as closed stops. Each item says how you get there:
`travelMins`, `travelMode` (`walk` | `transit` | `train`) and `travelKm`; null for the day's first stop without
an accommodation, or when a place has no coordinates.

## The traveller's own bookings (optional)

Trips can carry `stays` (where they're sleeping) and `transport` (flights, trains, buses... they've booked: the
way in, the way home, or between cities). Both are optional and editable with `PATCH /trips/{id}`.

- **Booked journeys** block time on their dates, with room either side: 2.5h before a flight and 75 min after
  (check-in, security, bags, getting into town); 30 min before and 20 min after a train. A stop that overlaps is
  moved to after it; an overnight flight blocks the end of one day and the start of the next.
- **Stays**: each day starts from where the traveller woke up (or checks in that day). The first stop gets a
  leg from the accommodation and starts no earlier than the day start plus that journey. Stays without
  coordinates are located with OpenStreetMap (Nominatim), searching in the country of that check-in date.
- Both go into the Gemini prompt as data (one line each, capped, marked "never instructions").
- `services/bookings.py` has the rules (`BEFORE` / `AFTER` minutes per kind).

## Changes made on the itinerary page

Voice or typed changes are made in the browser by Gemini (the front end's `/api/voice-edit`), whole days at a
time with new places inline. The page then sends the changed days to `POST /trips/{id}/itinerary/check`, which,
**without asking Gemini again**, runs the same checks as a generated plan: travel time (and bookings), opening
hours, public holidays, and costs converted to the home currency. The result says what it found in `problems`
(e.g. "Shibuya Sky moved to 11:45 to leave time to get there.") and is saved into the stored itinerary: new
stops become places (`origin='ai'`), existing ones are matched by name. The demo trip is checked but never
saved (`saved: false`); there the change stays in that browser.

## Run locally

```bash
cd backend
python -m venv .venv
.venv/Scripts/activate        # Windows (Git Bash); macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # fill in DATABASE_URL, GEMINI_API_KEY, GEMINI_MODEL (+ optional GOOGLE_MAPS_API_KEY)
python apply_schema.py        # creates tables + the fx_rates hypertable (safe to re-run)
python seed_demo.py           # creates/resets the demo trip t_demo0001
uvicorn app.main:app --reload --port 8000
```

Interactive docs: http://localhost:8000/docs

Tests: `python -m pytest -q` (API tests run against the DB in `DATABASE_URL` and clean up after themselves; they're skipped if it isn't set)

The password in `DATABASE_URL` can contain special characters like `@`; the app percent-encodes it.

## Reliability (M8)

- **Rate limits (per IP, in memory):** `POST /trips/{id}/itinerary` 10/min; `POST /trips` and
  `POST /trips/{id}/places` 60/min. Reads aren't limited. Over the limit: 429 `rate_limited`.
- **Gemini fallback:** models are tried in order (`GEMINI_MODEL`, then `GEMINI_FALLBACK_MODELS`). A model that
  hits its quota (429) is skipped for 15 min; an overloaded one (5xx) is skipped for that call.
- **Deadline:** one generation spends at most ~100s on Gemini. No new attempt starts with under 25s left;
  the request then fails fast with 503 `gemini_busy` instead of hanging. If the first plan alone took over 45s,
  the fix pass is skipped and any closed stops are shown as `closed`.
- **Timeouts:** every outbound call has one (Gemini 60s; Nominatim, Nager.Date, Frankfurter, Places 5s); DB connect
  5s and any single query 15s. Every external call is logged with its duration.
- **Errors never include stack traces:** unexpected errors return 500 `internal_error`; details go to the server log.

Error codes the front end may see (all `{ "error", "message" }`; `message` is safe to show the user):

| Status | `error` | Meaning |
|---|---|---|
| 403 | `read_only` | Tried to change the demo trip |
| 404 | `not_found`, `no_itinerary` | Unknown trip, or no itinerary generated yet |
| 422 | `date_outside_trip` | An edited day's date isn't one of the trip's days |
| 422 | `validation_error` | Bad request body; `message` says which field |
| 422 | `unknown_city` | A route city isn't a real place in that country (not in the dropdown's list) |
| 429 | `rate_limited` | Too many requests from this IP; try again shortly |
| 502 | `generation_failed` | Gemini returned an invalid itinerary twice |
| 503 | `gemini_quota`, `gemini_busy` | Gemini out of quota, or too slow/overloaded right now |
| 500 | `internal_error` | Anything unexpected |

**Demo trip:** `python seed_demo.py` creates/refreshes `t_demo0001` and generates its itinerary (keeps the old
itinerary if generation fails). `--no-generate` skips the Gemini call. Run it on the morning of the demo, after
the free Gemini quota resets (midnight Pacific = 08:00 London).

## Deploy (Vultr)

Ubuntu 24.04 VM. Uvicorn runs under **systemd** on `127.0.0.1:8000`; **Caddy** is the public entry point
and gets/renews the HTTPS certificate automatically. No Docker: one Python service and one web server,
nothing to build. Everything is in `backend/deploy/`.

**One-time setup**
1. Vultr: Ubuntu 24.04, London, add your SSH public key. Firewall group: allow TCP **22**, **80**, **443**.
2. DNS (Porkbun, for `tripezium.club`): `A` record `api` -> the server's IP (`65.20.109.66`).
3. From the repo root on your machine (replace the IP and domain):
   ```bash
   scp backend/.env root@<IP>:/root/iku.env
   ssh root@<IP> "curl -fsSL https://raw.githubusercontent.com/dnagasundhar-png/IKU_Trip_Planner/main/backend/deploy/setup.sh -o /root/setup.sh && bash /root/setup.sh api.<domain>"
   ```
   Without a domain yet, run `bash /root/setup.sh` (no argument): plain HTTP by IP, for testing only.
   Browsers block calls from the HTTPS front end to an HTTP API.

**Redeploy after pushing new code:** `ssh root@<IP> "bash /root/setup.sh api.<domain>"`
(pulls `main`, reinstalls deps, applies the schema, restarts). To try another branch: `BRANCH=<branch> bash /root/setup.sh api.<domain>`.

**Roll back to the last known-good version:** `ssh root@<IP> "BRANCH=v1-safe bash /root/setup.sh api.<domain>"`, then
`bash /root/setup.sh api.<domain>` to go back to `main`.

**Change a secret:** edit `backend/.env` locally, `scp` it to `/root/iku.env` again, re-run setup.

**Logs:** `ssh root@<IP> journalctl -u iku-api -f` · status: `systemctl status iku-api caddy`

## Endpoints

| Method + path | Notes |
|---|---|
| `GET /health` | `{ "status": "ok", "db": "ok" }`, or 503 with `"status": "degraded"` if the DB is unreachable |
| `POST /trips` | Body: Trip without `id`, optionally with a multi-city `route` (below). Returns 201 + full Trip. Without a route, resolves country + currency via Nominatim |
| `GET /trips/{id}` | Returns Trip |
| `PATCH /trips/{id}` | Send only the fields that changed (e.g. `route` after the user edits it). Validated like a new trip. Changing anything except `travellers` deletes the stored itinerary, so the next `GET /itinerary` returns `no_itinerary` and the front end regenerates. The demo trip is read-only (403) |
| `GET /trips/{id}/places` | `{ "places": [Place] }`: imported places first, then stops Gemini added. Use it to turn itinerary `placeId`s into names and map pins (re-fetch after each generation) |
| `POST /trips/{id}/places` | Body `{ "places": [Place] }`. Missing `id`s are assigned. Returns `{ "places": [Place] }` |
| `POST /trips/{id}/itinerary` | Generates (or regenerates) and stores the itinerary with Gemini. **Takes ~20-30s**: show a loading state. 502 `generation_failed` if Gemini fails twice |
| `GET /trips/{id}/itinerary` | Returns the stored itinerary (fast). 404 `no_itinerary` if none generated yet |
| `POST /trips/{id}/itinerary/check` | Body `{ "days": [{ "date", "city"?, "country"?, "items": [{ "time", "name", "localName"?, "category"?, "durationMins", "lat"?, "lng"?, "status"?, "localCost"?: Money, "estimatedCost"? }] }] }`: days the user changed. Returns `{ "saved": bool, "days": [{ "date", "city", "country", "holiday", "items": [... + "status", "cost", "travelMins", "travelMode", "travelKm"], "total", "problems": [string] }] }`. Times may move later (travel, bookings). Saves into the stored plan; never for the demo trip |

**Multi-city trips:** send `route`, the front end's `RouteStop` list in travel order:
`"route": [{ "city": "Paris", "country": "FR", "days": 2 }, { "city": "Rome", "country": "IT", "days": 1 }]`
(`country` = ISO alpha-2; extra keys such as `cityId` are ignored). The legs' `days` must add up to the trip's
length (422 otherwise), and `destination` stays as the display summary ("France & Italy"). With a route:
- each itinerary day gets a `city`, and Gemini plans that day's stops in that city (a later start on travel days)
- public holidays are fetched per country and applied only on the days spent there ("Christmas Day (FR)")
- costs come back in each city's own currency, converted to the home currency as before
- imports use every city on the route as context
No `route` (or `[]`) = a single-destination trip, exactly as before.

**Stays and booked journeys** (optional, on `POST` and `PATCH /trips`; send `[]` to clear):
```json
"stays": [{ "name": "Hotel Gracery Shinjuku", "address": null, "city": "Tokyo",
            "checkIn": "2026-12-30", "checkOut": "2027-01-02", "lat": null, "lng": null }],
"transport": [{ "kind": "flight", "origin": "London Heathrow", "destination": "Tokyo Haneda",
                "departs": "2026-12-29T19:00", "arrives": "2026-12-30T15:00", "reference": "BA7" }]
```
`kind`: `flight` | `train` | `bus` | `ferry` | `car` | `other`. Times are **local where it happens**,
`YYYY-MM-DDTHH:MM`; `arrives` is optional and must not be before `departs`; `checkOut` must not be before
`checkIn`. The response has the stays with the coordinates we found and the journeys sorted by departure.
Changing either replans, like a route change.

**Demo trip ID:** `t_demo0001` (Tokyo, 30 Dec 2026 to 2 Jan 2027, 2 travellers, GBP).

All JSON is camelCase. Errors are always `{ "error": "<code>", "message": "<text>" }`.
`estimatedCost` and `costHome` are **per person**.
